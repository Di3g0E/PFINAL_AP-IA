## Bloque A — Fix Telegram (EN CURSO)

**Causa probable**: instrucciones del frontend mencionan `@P6SecurityBot` pero el bot real es `@finances_guy_bot`. Usuario hace `/start` al bot equivocado → chat_id no es válido para el token configurado → Telegram devuelve "chat not found", pero `TelegramService.send_message` captura el error y `notify()` no propaga nada → endpoint responde 200 OK falsamente.

Pasos:
1. `TelegramService.send_message` → devuelve `(ok: bool, error_detail: Optional[str])` con el `description` real de la respuesta de Telegram.
2. `notify()` → devuelve dict por canal: `{telegram: ok|error|skipped, telegram_error: ..., whatsapp: ...}`.
3. `/api/user/test-notification` → si `telegram != ok` propaga como HTTP 502 con el error real.
4. Nuevo endpoint `GET /api/user/telegram-status` → diagnóstico (token presente, chat_id guardado, llamada `getMe` al bot → devuelve username y first_name del bot para verificar identidad).
5. `main.py` → eliminar el `include_router(settings_router.router, prefix="/telegram")` duplicado.
6. Frontend `/settings`: cambiar instrucciones `@P6SecurityBot` → `@finances_guy_bot`.
7. Frontend `/settings`: el botón "Probar" hace `await` del fetch y muestra el `detail` real del error.

## Bloque C — Fase 1: persistencia de chat (PRINCIPAL)

### C.1 — BD

Nuevas tablas en `src/data/schema.py` + migración en `scripts/init_db.py`:
- `chat_sessions(id UUID PK, user_id FK→users, title VARCHAR(120), summary TEXT NULL, created_at TIMESTAMPTZ, last_message_at TIMESTAMPTZ, archived BOOL DEFAULT false)`
- `chat_messages(id BIGSERIAL PK, session_id UUID FK→chat_sessions ON DELETE CASCADE, role VARCHAR(16), content TEXT, action VARCHAR(64) NULL, sequence INT, created_at TIMESTAMPTZ)`
- Índices: `(user_id, last_message_at DESC)` y `(session_id, sequence)`.

### C.2 — Endpoints

- `GET    /chat/sessions` → lista sesiones del usuario (id, title, last_message_at, archived).
- `POST   /chat/sessions` → crear nueva (title opcional; si vacío, se rellenará con el primer mensaje).
- `GET    /chat/sessions/{id}` → summary + últimos K=20 mensajes.
- `DELETE /chat/sessions/{id}` → borrado físico (cascada a messages).
- `PATCH  /chat/sessions/{id}` → rename / archive.

### C.3 — Modificar `POST /chat`

- Si `session_id` no existe en BD → crear con título derivado de los primeros 60 caracteres del mensaje.
- Persistir user message + assistant message tras la respuesta del grafo.
- Cada N=8 turnos: regenerar `summary` (LLM con prompt ASPECCT corto). Los mensajes más antiguos que K=20 se eliminan de `chat_messages` (quedan condensados en summary).
- Cuando hay `summary`, inyectarlo al grafo como `SystemMessage` antes de los mensajes recientes.
- Actualizar `last_message_at`.

### C.4 — Frontend

- `localStorage.current_session_id` persiste sesión activa.
- `/chat` al montar: si hay `current_session_id`, `GET /chat/sessions/{id}` y rehidrata turnos + sessionId.
- Sidebar (panel izquierdo) con histórico clicable.
- Botón "Nueva conversación" → POST + reset (deja `current_session_id` vacío hasta el primer mensaje).
- Recargar página o cambiar de pestaña: mantiene la conversación actual.
